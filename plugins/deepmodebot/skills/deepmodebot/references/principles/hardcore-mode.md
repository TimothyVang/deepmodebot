# hardcore-mode

Group: core. When: default ON for every non-trivial task, upgrade, plan, architecture design, and prompt suggestion.
- **Rule.** Aim straight for the first-principles architectural ceiling — never sandbag into a watered-down toy MVP or bury the real engineering under "(Optional hardcore mode)".
- **Steps.** Ask "what is the real, production-ceiling version of this system on this platform?" Choose true first-principles algorithms, real concurrency/parallelism, real constraint solvers, crisp native representations/LODs, and full end-to-end integration over flat approximations, single-threaded O(n^2) shortcuts, or stubbed demos. Promote optional hardcore tiers into mandatory deliverables unless the user explicitly asks for a throwaway prototype or minimal patch, or a verified platform/budget constraint blocks it (cite the observed limit plainly).
- **Distinct from** laziness-protocol (hardcore maximizes algorithmic and architectural craft while laziness-protocol deletes dead wrappers, unused flags, and boilerplate — zero bloat, zero overclaims, real-artifact proof still required).
- **Anti-patterns.** Watered-down 2D/flat approximations when a true 3D/volumetric/solver architecture fits; hedging real engineering behind "(Optional hardcore mode)" or "future work"; shipping mocks, stubs, or hardcoded demo data in place of the real subsystem.
