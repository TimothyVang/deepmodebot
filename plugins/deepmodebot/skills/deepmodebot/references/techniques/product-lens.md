# product-lens

**Use when:** challenging whether a planned feature or product is ambitious and sharp enough ("founder review", "product review", "think bigger", "10-star experience", "is this a painkiller or vitamin?") before locking a spec.

Where **grill** stress-tests technical failure modes and **tournament** explores architectural/research shapes, **product-lens** interrogates user value, wedge sharpness, and time-to-magic:

1. **Painkiller vs vitamin test.** Name the exact user, the painful moment that makes them switch *today*, and what they currently cobble together (spreadsheets, scripts, manual copy-paste). If the plan solves a mild inconvenience with high setup friction, call it out bluntly.
2. **60-second time-to-value audit.** Count every click, signup wall, config file, or empty-state hurdle between first open and the user's first "aha" artifact. Eliminate cold-start blank screens with instant sample data, zero-config defaults, or 1-command local runs.
3. **5-star → 10-star inversion.** State the current plan (5-star: does what was asked), the 7-star version (removes adjacent manual drudgery automatically), and the 10-star ceiling (solves the underlying job end-to-end with verifiable proof), then pick the highest-leverage wedge that ships cleanly without scope bloat.
4. **Cut / Keep / Amplify table.** Classify every proposed item into **Cut** (settings/chrome/premature multi-tenancy nobody asked for), **Keep** (minimum viable spine), or **Amplify** (the 1–2 differentiating capabilities where craft creates unfair advantage).

**Done when** the user persona, switching trigger, 60-second value path, 10-star inversion, and explicit Cut/Keep/Amplify table are written cleanly and fed into the spec or build plan.
